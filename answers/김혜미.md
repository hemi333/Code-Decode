# 1주차 · 1단계 답

## 1. system 을 지우면 답변이 어떻게 달라지는가

달라지는 것은 **내용이 아니라 형태**다. `sorted()` 와 `list.sort()` 의 차이라는 사실
자체는 양쪽 다 똑같이 맞게 나온다. 대신:

- **길어진다.** "짧고 정확하게 답합니다" 라는 제약이 사라지니 예시 코드가 여러 개
  붙고, 마크다운 표와 불릿이 늘어나고, 사족이 붙는다.
- **출력 토큰이 늘고 비용이 오른다.** 출력은 입력의 5배 단가($10 vs $2 per 1M)라
  비용에 바로 온다.
- **톤이 바뀐다.** "파이썬을 가르치는 사람" 이라는 배역이 사라지고 범용 어시스턴트
  말투가 된다.

교훈 — **system 은 출력 길이와 형식을 통제하는 가장 값싼 레버다.** 한 문장 추가하는
입력 비용은 무시할 만한데, 그것이 매 응답의 출력 토큰을 좌우한다. 그리고 이 문장은
*매 요청마다 통째로 다시 전송된다.* 모델이 기억하는 게 아니라 우리가 계속 다시 보낸다.

### 실측에서 확인된 것

| | 입력 토큰 | 출력 토큰 | stop_reason |
|---|---|---|---|
| system 있음 | 75 | 512 | `max_tokens` |
| system 없음 | 38 | 512 | `max_tokens` |

입력 토큰이 75 → 38 로 줄었다. 그 차이 37개가 곧 system 프롬프트의 무게다.

**다만 이 비교는 반쪽짜리다.** 양쪽 다 `max_tokens=512` 상한에 걸려 잘렸기 때문에
"system 이 있으면 더 짧아진다"는 것을 출력 토큰 수로는 확인할 수 없었다. 둘 다
천장에 닿았을 뿐이다. 제대로 비교하려면 `max_tokens` 를 넉넉히(예: 2048) 주고
`stop_reason` 이 양쪽 다 `end_turn` 이 되게 한 뒤 출력 토큰을 재야 한다.

→ 다시 해볼 것.

## 2. max_tokens 를 30 으로 줄이면 stop_reason 은?

`max_tokens` 로 바뀐다.

| 값 | 의미 |
|---|---|
| `end_turn` | 모델이 할 말을 다 하고 스스로 멈췄다 |
| `max_tokens` | 아직 할 말이 남았는데 우리가 정한 상한에 부딪혀 잘렸다 |

실제로 본문이 `# sorted() vs list.sort()` 제목과 `##` 까지만 나오고 끊겼다.
`출력 토큰: 30` — 정확히 상한만큼 쓰고 멈췄다.

### 여기서 진짜 중요한 것

> **잘린 응답은 에러가 아니다.** HTTP 200 이고 예외가 발생하지 않는다.
> `try/except` 로는 절대 못 잡는다.

즉 `stop_reason` 을 직접 확인하지 않으면 잘린 줄도 모르고 그 반토막을 다음 단계로
넘기게 된다. 실무 코드에 이런 분기가 필요한 이유다:

```python
if response.stop_reason == "max_tokens":
    ...  # 재시도하거나, 상한을 늘리거나, 최소한 로그를 남긴다
```

그리고 잘린 응답에도 돈은 낸다.

한 가지 더 — Sonnet 5 는 `thinking` 인자를 넘기지 않으면 adaptive thinking 이
켜진 채로 돈다. `max_tokens=30` 이면 thinking 토큰만으로 30 을 다 써버려서 text
블록이 아예 안 나올 수도 있다. 그러면 화면에 빈 줄만 찍힌다. 에러가 아니라 그냥
빈 화면이다. 같은 교훈의 연장.

## 3. 여러 턴 대화는 누가 기억하는가

**우리가 기억한다.** 정확히는 `messages` 리스트가 기억 그 자체다.

API 는 **stateless** 다. 서버에 세션이 없고, 모델은 이전에 무슨 말을 했는지 전혀
모른다. 3턴째 요청을 보낼 때 우리는 1턴·2턴의 내용을 **전부 다시 보낸다.**

```python
messages = [
    {"role": "user",      "content": "질문 1"},
    {"role": "assistant", "content": "답 1"},      # 지난 응답을 우리가 넣어준 것
    {"role": "user",      "content": "질문 2"},    # ← 이번에 보내는 것
]
```

여기서 나오는 두 가지 결과.

**첫째, 대화가 길어질수록 입력 토큰이 누적된다.** 매 턴 전체 history 를 다시
보내니까. 10턴짜리 대화의 마지막 호출은 1턴째보다 훨씬 비싸다. 프롬프트 캐싱이
존재하는 이유가 이것이다.

**둘째 — 이게 4단계의 전부인데 — 루프란 결국 `messages` 에 계속 append 하는 일이다.**

```
모델 응답을 messages 에 append          →  "모델이 이렇게 말했다"
도구를 실행한 결과를 messages 에 append  →  "그래서 이런 결과가 나왔다"
다시 호출                               →  전체를 다시 보낸다
```

그리고 `step4_loop.py` 주석이 강조하는 그 대목 — `response.content` 를 **통째로**
넣어야 하는 이유가 여기서 나온다. 텍스트만 뽑아 문자열로 넣으면 `tool_use` 블록의
`id` 가 사라지고, 그러면 "어느 호출에 대한 결과인지" 짝을 맞출 수 없게 된다.
기억을 우리가 들고 있으니, 기억을 훼손하는 것도 우리다.

## 겪은 문제와 해결

1. **401 `API key is invalid`** — `.env` 에 실제 키가 아니라 자리표시자
   `sk-ant-...` 가 들어 있었다. 콘솔에서 키를 발급받아 교체.

2. **400 `anthropic-workspace-id is required`** — 콘솔에서 발급한 키가
   워크스페이스 키가 아니라 사용자(identity)에 연결된 키였다. 이런 키는 어느
   워크스페이스로 보내는 요청인지 헤더로 매번 알려줘야 한다.
   `env.workspace_headers()` 를 만들어 클라이언트 생성 지점에 붙였다.
   → 커밋 `580d210`

3. **`AttributeError: 'ThinkingBlock' object has no attribute 'text'`** —
   `response.content[0].text` 가 터졌다. Sonnet 5 는 답하기 전에 스스로 생각하고,
   그 흔적이 thinking 블록으로 리스트 맨 앞에 들어온다. thinking 블록에는 `.text`
   가 없다. **'몇 번째 블록'이 아니라 'type 이 무엇인지'로 골라야 한다:**

   ```python
   print("\n".join(b.text for b in response.content if b.type == "text"))
   ```

   교재가 쓰인 시점보다 모델이 앞서간 경우. 3단계에서 `tool_use` 블록이 섞여
   들어올 때 같은 문제를 다시 만나게 된다 — 그때도 `[0]` 은 통하지 않는다.
